لاحقاً من أنواع طلبات: عمود `type` قابل للتوسّع، والصلاحيات الأربع مهيّأة سلفاً.

## مسار الاعتماد

```php
/** مسار الاعتماد: الموظف ← الآليات ← المدير العام. */
public const STAGES = ['fleet', 'gm'];
```

```
الموظف يقدّم
   │  status = pending_fleet, stage = fleet
   ▼
فرع الآليات ──رفض──► rejected · stage = done · إشعار لصاحبها
   │ موافقة
   ▼  status = pending_gm, stage = gm
المدير العام ──رفض──► rejected · stage = done
   │ موافقة
   ▼  status = approved, stage = done, decided_at = now()
تُولَّد وثيقة Word + PDF موقّعة بتوقيع المعتمِد
```

الحالات الخمس: `pending_fleet` · `pending_gm` · `approved` · `rejected` · `cancelled`.
والمراحل الثلاث: `fleet` · `gm` · `done`.

**الرفض ينهي المسار فوراً** ولا يعيد الطلب خطوةً إلى الوراء — يعود إلى صاحبه مباشرةً
مع سبب الرفض إن كُتب. السحب (`cancel`) متاح لصاحب المهمة ولفرع الآليات ما دامت مفتوحة.

> `statusForStage()` يبني الحالة من المرحلة: `'pending_' . $stage`، وعند انتهاء
> المراحل تصير `approved`. مصدر واحد للحقيقة بدل جدول تحويل يدوي.

## من يرى ومن يبتّ

`FleetAccessService` هو المرجع الوحيد لذلك:

| السؤال | الجواب |
| --- | --- |
| من يُعدّ «موظف آليات»؟ | من يملك `fleet.manage`، **أو** من قسمه ضمن أقسام الفرع |
| من يرى مهمة بعينها؟ | صاحبها · موظفو الآليات · المدير العام — **لا أحد غيرهم** |
| من يبتّ في مرحلة `fleet`؟ | موظف آليات، أو من يملك `fleet.approve` |
| من يبتّ في مرحلة `gm`؟ | `role === 'general_manager'` حصراً |

```php
/** الاطلاع على المهمة حكرٌ على صاحبها وفرع الآليات والمدير العام. */
public function canView(?User $user, FleetMission $mission): bool
{
    return (int) $mission->user_id === (int) $user->id
        || $this->isFleetStaff($user)
        || $user->role === 'general_manager';
}
```

> **رؤساء الأقسام لا يرون مهام موظفيهم.** هذا فرق جوهري عن التقارير والمهام،
> وهو مقصود: المهمة شأن بين الموظف وفرع الآليات والإدارة العامة.

### كيف يُعرَف قسم الآليات

```php
/** يُعرَف فرع الآليات بالرمز FLEET أو بورود أحد هذه الأسماء فيه. */
private const FLEET_KEYWORDS = ['آليات', 'الآليات', 'اليات', 'fleet', 'vehicles'];
```

المطابقة بالرمز `FLEET` أو بالاسم، فلا تنكسر الوحدة إن أُنشئ القسم يدوياً برمز مختلف.

## اللوحة الواحدة بثلاثة وجوه

`GET /api/fleet/missions` يخدم شاشتين مختلفتين حسب هوية الطالب:

| الطالب | ما يراه | أدوات الإدارة |
| --- | --- | --- |
| موظف آليات | كل المهام بكل الحالات | نعم (تسجيل نيابةً، قائمة الموظفين) |
| المدير العام | `pending_gm` · `approved` · `rejected` فقط | لا |
| غيرهما | ‏403 | — |

الاستجابة تحمل معها `summary` جاهزاً (الإجمالي · المعلّق · المعتمد · المرفوض ·
ما ينتظر المرحلة الحالية للطالب) حتى لا تحسبه الواجهة.

`GET /api/fleet/my-missions` منفصل: مهام الطالب الشخصية لا غير، ومعها
`is_fleet_staff` لتقرّر الواجهة أي لوحة تعرض.

## الرقم المرجعي

```php
return 'FL-' . now()->format('Ymd') . '-' . str_pad((string) $this->fleet->nextDailySequence(), 4, '0', STR_PAD_LEFT);
```

مثال: `FL-20260922-0003` — ثالث مهمة في ذلك اليوم. التسلسل يومي، يُحسب بعدّ مهام
اليوم لا بعدّاد مستقل.

> **الرقم المرجعي لا يتغيّر أبداً بعد إصداره.** ترحيل النقل من الموارد البشرية
> احتفظ بالأرقام كما صدرت كي تبقى الوثائق المطبوعة مطابقةً لسجلها في النظام.

## التحقق من المدخلات

`StoreFleetMissionRequest`:

```php
'user_id'     => ['nullable', 'integer', 'exists:users,id'],
'type'        => ['nullable', Rule::in(FleetMission::TYPES)],
'start_date'  => ['required', 'date'],
'end_date'    => ['required', 'date', 'after_or_equal:start_date'],
'days'        => ['nullable', 'numeric', 'min:0', 'max:365'],
'destination' => ['required', 'string', 'max:180'],
'reason'      => ['required', 'string', 'max:2000'],
'attachment'  => ['nullable', 'file', 'max:20480', 'mimes:pdf,doc,docx,png,jpg,jpeg'],
```

خلافاً لطلبات الموارد البشرية، **التاريخان والجهة المقصودة إلزامية دائماً** — لأن
الوحدة نوع طلب واحد لا أنواعاً متعددة الحقول.

`days` تُحسب في الخادم إن لم تُرسل: `diffInDays + 1` (يوم البداية محسوب).

### التسجيل نيابةً عن موظف

```php
// التسجيل نيابةً عن موظف آخر حكرٌ على فرع الآليات.
abort_unless($targetId === (int) $actor->id || $this->access->isFleetStaff($actor), 403, ...);
```

## الوثيقة

تُولَّد عند الاعتماد النهائي فقط، داخل المعاملة نفسها:

```
document_number ← تسلسل الوثائق
qr_payload      ← 'CND-FLEET:' . document_number
word_path       ← fleet-missions/generated/Y/m/d/mission-<id>-<uniqid>.docx
pdf_path        ← تحويل عبر DocxPdfConverter
```

التوقيع يُدرج من صورة توقيع المعتمِد إن وُجدت، وإلا يُفرَّغ مكانه في القالب بدل
ترك اسم الحقل ظاهراً.

> **القالب:** `config/document_templates.php` → `fleet.mission_approval`
> (‏`resources/templates/documents/fleet/mission-approval.docx`). القالب لم يصدر بعد،
> و`FleetDocumentService::template()` يتراجع إلى قالب طلبات الموارد البشرية،
> وإن غاب الاثنان لا تُولَّد وثيقة **دون أن تفشل العملية**.

## الإشعارات

| الحدث | من يُشعَر |
| --- | --- |
| تقديم مهمة | أصحاب المرحلة الحالية (فرع الآليات) |
| موافقة مرحلية | صاحب المهمة + أصحاب المرحلة التالية |
| اعتماد نهائي | صاحب المهمة + أطراف المسار (عدا صاحبها) |
| رفض | صاحب المهمة + أطراف المسار (عدا الرافض وصاحبها) |

«أطراف المسار» = موظفو الآليات + المدير العام (`watcherIds()`).

## الصلاحيات

| الصلاحية | المعنى | كيف تُمنح |
| --- | --- | --- |
| `fleet.request` | تقديم مهمة | بالدور — لكل الأدوار التي تقدّم طلبات |
| `fleet.view` | فتح لوحة الفرع | بالدور لـ `general_manager`؛ وللأشخاص في الفرع |
| `fleet.manage` | أدوات الإدارة والتسجيل نيابةً | **للأشخاص مباشرةً** لا بالدور |
| `fleet.approve` | البتّ في مرحلة الآليات | **للأشخاص مباشرةً** لا بالدور |

> منح `manage` و`approve` للأشخاص لا للأدوار **مقصود**، كما في الموارد البشرية:
> العضوية في الفرع شخصية لا وظيفية. لا تضِفهما إلى دور في `RolePermissionSeeder`.

php artisan db:seed --class=FleetSeeder
