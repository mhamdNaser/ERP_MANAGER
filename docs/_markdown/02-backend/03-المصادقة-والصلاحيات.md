# المصادقة والصلاحيات والنطاق

النظام يحمي البيانات بثلاث طبقات مستقلة. فهم الفرق بينها ضروري قبل أي تعديل.

```
┌─────────────────────────────────────────────────────────────┐
│ 1. المصادقة (Authentication)  ── من أنت؟                    │
│    AuthenticateApiToken.php                                 │
│    الفشل ← 401                                              │
├─────────────────────────────────────────────────────────────┤
│ 2. الصلاحية (Permission)      ── هل يُسمح لك بهذا النوع من  │
│    permission: middleware        العمليات إطلاقاً؟           │
│    الفشل ← 403                                              │
├─────────────────────────────────────────────────────────────┤
│ 3. النطاق (Scope)             ── وعلى أي سجلات تحديداً؟     │
│    *ScopeService / *AccessService                           │
│    الفشل ← قائمة فارغة أو 422                               │
└─────────────────────────────────────────────────────────────┘
```

مثال يوضّح الفرق: رئيس قسم يملك `reports.view` (صلاحية)، لكن النطاق يحصر ما يراه
في تقارير قسمه التي حالتها `department_review` فقط.

## 1. المصادقة

### تسجيل الدخول — `Modules/Core/Controllers/SystemController.php::login()`

```php
$user = User::with([...])->where('email', ...)->where('is_active', true)->first();
if (! $user || ! Hash::check($request->validated('password'), $user->password)) {
    return response()->json(['message' => __('messages.invalid_credentials')], 422);
}
$plainToken = Str::random(64);
$user->update(['api_token' => hash('sha256', $plainToken)]);
return response()->json(['token' => $plainToken, 'user' => new UserResource($user)]);
```

| الخطوة | التفصيل |
| --- | --- |
| شرط `is_active` | الحساب المعطّل لا يستطيع الدخول أصلاً |
| رسالة موحّدة | لا تفرّق بين بريد خاطئ وكلمة مرور خاطئة — لا تسريب لوجود الحساب |
| توليد التوكن | `Str::random(64)` عشوائي مشفّر آمن |
| التخزين | `hash('sha256', $plainToken)` — الخام لا يُحفظ |
| الإرجاع | التوكن الخام يُرسل مرة واحدة فقط |

> **توكن واحد لكل مستخدم.** تسجيل الدخول من جهاز ثانٍ يستبدل التوكن ويُخرج الأول.
> هذا سلوك مقصود وبسيط. لو أردت جلسات متعددة فستحتاج جدولاً منفصلاً للتوكنات.

### الخروج — `SystemController::logout()`

```php
$request->user()->update(['api_token' => null]);
```

يُبطل التوكن على الخادم فوراً. الفرونت يحذفه من `localStorage` في `App.jsx`.

### استعادة الجلسة — `SystemController::me()`

`FrontEnd/src/App.jsx` عند الإقلاع: إن وُجد `cnd_token` يستدعي `GET /api/auth/me`.
الفشل يمسح التوكن ويعرض شاشة الدخول.

### كلمة المرور

`app/Models/User.php` يضبط `'password' => 'hashed'` في `casts()`، فأي إسناد لكلمة
مرور يُشفَّر تلقائياً. لا تستدعِ `Hash::make()` يدوياً — ستشفّرها مرتين.

الحقول المخفية:

```php
protected $hidden = ['password', 'remember_token', 'api_token'];
```

## 2. الأدوار والصلاحيات

### الأدوار السبعة

| الدور | الوصف | نطاقه العام |
| --- | --- | --- |
| `employee` | موظف | نفسه فقط |
| `technician` | فني — نفس صلاحيات الموظف | نفسه فقط |
| `department_head` | رئيس قسم | قسمه |
| `branch_manager` | مدير فرع | فرعه وأقسامه |
| `general_manager` | مدير عام | المؤسسة كاملة |
| `database_manager` | مدير قواعد بيانات | المؤسسة كاملة + صلاحيات تقنية |
| `office_manager` | مدير مكتب | مذكور في ترحيلات المنح |

`app/Models/User.php` يوفّر:

```php
public function primaryRole(): string { return $this->getRoleNames()->first() ?? $this->role; }
```

يفضّل دور spatie ويسقط إلى عمود `users.role` عند غيابه. **استخدم `primaryRole()` دائماً**
في منطق النطاق، لا `$user->role` مباشرة.

> استثناء موجود في الشيفرة: `Modules/Hr/Services/HrAccessService.php` يقارن
> `$user->role === 'general_manager'` مباشرةً. هذا يعمل لأن العمود مضبوط في البذور،
> لكن الأسلم في الكود الجديد هو `primaryRole()`.

### الصلاحيات — المصدر `database/seeders/RolePermissionSeeder.php`

| المجموعة | الصلاحيات |
| --- | --- |
| التقارير | `reports.view`, `reports.create`, `reports.update.returned`, `reports.transition`, `reports.export.personal`, `reports.export.department`, `reports.export.branch` |
| الإشعارات | `notifications.view` |
| الرسائل | `messages.view`, `messages.create`, `messages.reply` |
| المراسلات الرسمية | `formal_correspondences.view`, `.create`, `.route`, `.delete` |
| التعاميم | `circulars.view`, `circulars.create` |
| المكاتب | `offices.manage` |
| الصلاحيات | `roles.permissions.manage` |
| المهام | `tasks.delete_with_activities` |
| الهيكل التنظيمي | `organization.view`, `branches.create/update/delete`, `departments.create/update/delete` |
| الموظفون | `employees.view`, `employees.create`, `employees.update`, `employees.delete` |
| قاعدة البيانات | `database.backups.manage` |
| الفورمات | `forms.view`, `forms.publish`, `forms.submissions.view`, `forms.export`, `forms.manage` |
| الموارد البشرية | `hr.view`, `hr.manage`, `hr.request`, `hr.approve` |

### الفرض في المسار

```php
Route::get('reports', [ReportController::class, 'index'])
    ->middleware('permission:reports.view');
```

صيغة "أو" بالخط العمودي — من `Modules/Communications/Routes/api.php`:

```php
->middleware('permission:messages.view|correspondences.view')
```

موجودة للتوافق مع أسماء الصلاحيات قبل إعادة تسمية "المراسلات" إلى "الرسائل".

### الفحص في الشيفرة

```php
if ($user->can('hr.manage')) { ... }
if ($user->hasRole('general_manager')) { ... }
```

مثال حقيقي في `Modules/Hr/Services/HrAccessService.php::isHrStaff()`.

### إضافة صلاحية جديدة — الخطوات الثلاث

**1.** أضف الاسم إلى `$permissions` في `RolePermissionSeeder.php` واربطه بالأدوار في `$roles`.

**2.** أنشئ ترحيل منح للبيئات القائمة (البذور لا تُعاد على الإنتاج). النمط من
`2026_08_02_000001_grant_hr_view_to_general_manager.php`:

```php
$permission = Permission::firstOrCreate(['name' => 'assets.view', 'guard_name' => 'web']);
Role::where('name', 'general_manager')->first()?->givePermissionTo($permission);
app()[\Spatie\Permission\PermissionRegistrar::class]->forgetCachedPermissions();
```

**السطر الأخير إلزامي** — بدونه تبقى الصلاحية القديمة في الكاش.

**3.** أضف وصفاً عربياً في `FrontEnd/src/i18n/permissionDescriptions.js` لتظهر مفهومة
في شاشة إدارة الصلاحيات.

## 3. خدمات النطاق

### `OrganizationScopeService` — الهيكل التنظيمي

`app/Modules/Organization/Services/OrganizationScopeService.php`

```php
public function employees(User $actor): Builder
{
    return match ($actor->primaryRole()) {
        'general_manager', 'database_manager' => User::query(),
        'branch_manager'  => User::where('branch_id', $actor->branch_id),
        'department_head' => User::where('department_id', $actor->department_id),
        default           => User::whereKey($actor->id),
    };
}
```

| الدالة | ترجع |
| --- | --- |
| `employees()` | استعلام الموظفين المرئيين |
| `branches()` | استعلام الفروع المرئية |
| `departments()` | استعلام الأقسام المرئية |
| `canManageBranch()` | هل يديره؟ |
| `canManageDepartment()` | هل يديره؟ |
| `canManageEmployee()` | هل يديره؟ |
| `canAssignRole()` | هل يحق له إسناد هذا الدور؟ مدير الفرع محصور بـ`employee`, `technician`, `department_head` |

**نمط مهم:** الدوال ترجع `Builder` لا `Collection`. هذا يسمح بإضافة فلاتر وترقيم
بعدها بلا جلب كل الصفوف. اتبع النمط نفسه في أي خدمة نطاق جديدة.

### `ReportAccessService` — التقارير

`app/Modules/Reports/Services/ReportAccessService.php`

```php
return match ($user->primaryRole()) {
    'database_manager' => $query,
    'general_manager'  => $query->whereIn('status', ['general_review', 'approved']),
    'branch_manager'   => $query->where('branch_id', $user->branch_id)->where('status', 'branch_review'),
    'department_head'  => $query->where('department_id', $user->department_id)->where('status', 'department_review'),
    default            => $query->where('employee_id', $user->id)->whereIn('status', ['draft', 'returned']),
};
```

هنا النطاق **يجمع الانتماء التنظيمي مع الحالة**. رئيس القسم لا يرى تقارير قسمه كلها،
بل ما ينتظر مراجعته فقط. هذا سبب اختفاء التقرير من قائمته بعد تحويله.

### `HrAccessService` — الموارد البشرية

`app/Modules/Hr/Services/HrAccessService.php`

نطاق مختلف تماماً: لا يعتمد الهرم التنظيمي بل **عضوية قسم الموارد البشرية**.

```php
public const HR_KEYWORDS = ['موارد بشرية', 'الموارد البشرية', 'human resources'];

public function hrDepartmentIds(): array
{
    return Department::query()
        ->where(fn ($q) => $q->where('code', 'HR')
            ->orWhere('name', 'like', '%موارد بشرية%') /* ... */)
        ->pluck('id')->all();
}
```

| الدالة | الغرض |
| --- | --- |
| `isHrStaff()` | عضو في قسم HR أو يملك `hr.manage` |
| `canDecide()` | هل يبتّ في المحطة الحالية؟ `hr` ← موظف HR، `gm` ← المدير العام |
| `canView()` | صاحب الطلب أو HR أو المدير العام — **لا رؤساء الأقسام** |
| `stageApprovers()` | المعنيّون بالمحطة الحالية، لإرسال الإشعارات |
| `watchers()` | HR + المدير العام مجتمعين |
| `pendingForUser()` | الطلبات التي تنتظر قرار هذا المستخدم |

> **قسم HR يُكتشف بالاسم أو الرمز.** إن أعاد أحدهم تسمية القسم بما لا يطابق
> `HR_KEYWORDS` ولا الرمز `HR`، سيفقد موظفوه الوصول. عند نقل النظام لمؤسسة أخرى راجع هذا الثابت.

## أخطاء شائعة عند التعديل

| الخطأ | لماذا خطر | الصواب |
| --- | --- | --- |
| إخفاء زر في الواجهة فقط | الـAPI ما زال مكشوفاً للاستدعاء المباشر | افرض في المسار والخدمة |
| `$user->role` بدل `primaryRole()` | يتجاهل أدوار spatie | استخدم `primaryRole()` |
| نسيان `forgetCachedPermissions()` | الصلاحية الجديدة لا تُطبَّق | استدعِها بعد كل تعديل |
| فحص الملكية في المتحكم فقط | يتكرر ويُنسى في مسار آخر | ضعه في خدمة نطاق |
| إرجاع `Collection` من خدمة نطاق | يمنع الفلترة والترقيم لاحقاً | أرجع `Builder` |
| إضافة صلاحية في البذور فقط | الإنتاج لا يعيد تشغيل البذور | أضف ترحيل منح أيضاً |
