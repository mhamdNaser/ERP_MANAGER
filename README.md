# CND Manager

نظام داخلي لإدارة التقارير اليومية والأسبوعية وخطط العمل ضمن تسلسل الصلاحيات المؤسسي.

## التشغيل المحلي

```powershell
cd BackEnd
php artisan serve --host=127.0.0.1 --port=8000

cd ..\FrontEnd
npm run dev -- --host 127.0.0.1 --port 5173
```
GIS@manager?2026
افتح `http://127.0.0.1:5173`. تبدأ الواجهة بفحص اتصال الخادم وقاعدة البيانات قبل إظهار تسجيل الدخول.

للرسائل الفورية شغّل Laravel Reverb بجانب خادم Laravel:

```powershell
cd BackEnd
php artisan reverb:start --host=127.0.0.1 --port=8080
```

### الانتقال إلى اسم CND

- الاسم المعتمد في الواجهات والباك أند والطباعة والتصدير والنسخ الاحتياطية هو `CND`.
- ترحيل `2026_06_14_000002_rename_ncm_brand_to_cnd.php` يحافظ على توافق البيانات القديمة، ويعيد تسمية جدول الإشعارات ويحدّث البريد الوظيفي وأرقام الموظفين القديمة.
- تغيّر مفتاح جلسة المتصفح إلى `cnd_token`، لذلك يلزم تسجيل الدخول مرة واحدة بعد التحديث.

## البنية

- `FrontEnd`: React 19 + Vite + JavaScript + Tailwind CSS + React Query، واجهة RTL وتنبيهات صوتية وتصدير Word/PDF.
- بنية الفرونت مقسمة إلى `Page` و`Components` و`Layout` و`Provider` و`Api` و`Apihooks` و`i18n`، بينما `App.jsx` مسؤول عن بوابة الاتصال والمصادقة وتركيب التطبيق.
- Tailwind مستخدم تدريجياً في العناصر الجديدة، مع إبقاء `index.css` والثيم الحالي دون تفعيل Preflight حتى لا يتغير المظهر.
- ترجمة محتوى الواجهة موجودة في `FrontEnd/src/i18n/translations.js` وتغيّر النصوص والاتجاه بالكامل بين العربية والإنجليزية.
- الشعار العام معتمد من `FrontEnd/src/assets/logo.jpg`.
- `BackEnd`: Laravel 12، نطاق المؤسسة داخل `app/Modules/Organization`.
- الرسائل الداخلية مفصولة عن المراسلات الرسمية: الرسائل تعتمد Reverb للتحديث الفوري، بينما المراسلات الرسمية تعتمد سجل زمني ووثائق متعددة.
- `ReportAccessService`: نقطة مركزية لتطبيق نطاق وصول التقارير والخطط حسب الدور.
- إعداد الإنتاج الافتراضي في `.env.example` يستخدم PostgreSQL.
- `BackEnd/scripts/postgres-provision.sql` ينشئ قاعدة `cnd_manager` وثلاثة مستخدمين: مالك، تطبيق قراءة/كتابة، وقارئ فقط.
- `config/database.php` يحتوي اتصالات `pgsql` و`pgsql_owner` و`pgsql_readonly` استعداداً لتعدد قواعد البيانات.
- بيئة التطوير الحالية تبقى SQLite إلى أن يتم تثبيت وتشغيل PostgreSQL Server محلياً؛ وجود pgAdmin وحده لا يشغّل محرك قاعدة البيانات.
- الأدوار والصلاحيات مبنية على `spatie/laravel-permission`.
- مسارات الباك أند منظمة على نمط Modules مع Requests وResources وRepositories وInterfaces وService Providers.
- اللغتان العربية والإنجليزية متاحتان عبر `X-Language` و`/api/locale/{lang}`.

## نطاق إدارة الهيكل التنظيمي

| الدور | الفروع | الأقسام | الموظفون |
| --- | --- | --- | --- |
| المدير العام | إدارة كاملة | إدارة كاملة | إدارة كاملة |
| مدير قواعد البيانات | إدارة كاملة | إدارة كاملة | إدارة كاملة، مع صلاحيات كاملة على التقارير والخطط |
| مدير الفرع | عرض فرعه | إدارة أقسام فرعه | إدارة موظفي فرعه |

تطبق هذه الحدود داخل `OrganizationScopeService` وفي طبقة Repositories، ولا تعتمد على إخفاء عناصر الواجهة فقط.

## بيانات الموظف الاختيارية

بيانات الموظف الإضافية منفصلة عن جدول `users` بعلاقات one-to-one:

- `user_addresses`: العنوان.
- `user_family_details`: البيانات العائلية وجهة اتصال الطوارئ.
- `user_personal_details`: تاريخ الميلاد والطول والوزن وفصيلة الدم.
- `user_clothing_sizes`: مقاسات الحذاء والبنطال والقميص والسترة.

يمكن إنشاء أو تحديث هذه البيانات كحقول nested اختيارية مع API الموظفين.

## تهيئة PostgreSQL

يتطلب المشروع PostgreSQL Server يعمل على `127.0.0.1:5432`. برنامج pgAdmin هو واجهة إدارة ولا يتضمن خادم قاعدة بيانات.

بعد تثبيت الخادم، غيّر كلمات المرور داخل `BackEnd/scripts/postgres-provision.sql` ثم شغّل:

```powershell
& "C:\Program Files\pgAdmin 4\runtime\psql.exe" -h 127.0.0.1 -p 5432 -U postgres -f BackEnd\scripts\postgres-provision.sql
```

بعدها استخدم `BackEnd/.env.postgresql.example` كأساس للإعداد، وشغّل migrations بحساب `cnd_owner` ثم أعد حساب التشغيل إلى `cnd_app`.

# الدليل التقني الكامل للمشروع

هذا القسم يكمّل المعلومات السابقة ولا يستبدلها. الغرض منه أن يستطيع أي مطور جديد فهم النظام، تحديد مكان التعديل، وتتبع رحلة البيانات من الواجهة حتى قاعدة البيانات دون الحاجة لقراءة المشروع كاملاً أولاً.

## 1. الصورة العامة والمعمارية

المشروع تطبيق داخلي من جزأين مستقلين:

```text
المتصفح
  │
  ├── FrontEnd / React + JavaScript + Vite + Tailwind CSS
  │     └── Api/http.js يرسل HTTP JSON أو FormData
  │
  └── BackEnd / Laravel REST API
        ├── Middleware: اللغة + مصادقة التوكن
        ├── Controllers: استقبال الطلب وإرجاع الاستجابة
        ├── Form Requests: التحقق والصلاحيات
        ├── Services: قواعد النطاق والأعمال المركبة
        ├── Repositories: الوصول المنظم للبيانات
        ├── Resources: تشكيل JSON
        └── Models + Database
```

- مسارات الواجهة تُعرّف داخل `FrontEnd/src/Apihooks/route.jsx` باستخدام `react-router-dom`، و`AppShell.jsx` يدير التبويبات الداخلية المسموحة حسب الدور.
- المصادقة تعتمد توكن عشوائي مخزن في `users.api_token` ويرسل عبر `Authorization: Bearer`.
- جميع حدود الوصول الحساسة تطبق في الباك إند عبر الصلاحيات وخدمات النطاق، ولا تعتمد على إخفاء عناصر الواجهة.
- ردود الـ API الأساسية JSON، بينما الرفع يستخدم `FormData` والتنزيل يستخدم `Blob`.
- الواجهة ثنائية اللغة وRTL/LTR، واللغة تحفظ محلياً وتُرسل للخادم في `X-Language`.

### نقاط الدخول والملفات العامة

- `src/main.jsx`: يركب `RouterProvider` و`QueryClientProvider` على عنصر الصفحة الجذري ويحمّل `index.css`.
- `src/App.jsx`: ينفذ ثلاث مراحل: فحص اتصال النظام، استعادة جلسة محفوظة أو تسجيل الدخول، ثم فتح `AppShell`. عند تسجيل الدخول أو الخروج يفرغ كاش React Query حتى لا تظهر بيانات حساب سابق.
- `src/Layout/AppShell.jsx`: قلب الواجهة؛ يحمل بيانات الداشبورد والتقارير والإشعارات، يبني القائمة حسب الصلاحيات، يعرض قائمة الحساب في التوب بار، ويدير سايدبار الموبايل القابل للتمرير.
- `src/lib.js`: ملف توافق صغير يعيد تصدير `api` والتخزين والصوت والتصدير، حتى تبقى الاستيرادات الحالية بسيطة.
- `src/Api/api.js`: تعريف endpoints مجمعة حسب النطاق: النظام، المهام، الملفات، التقارير، الفورمات، التواصل، المؤسسة، والإدارة.
- `src/Api/http.js`: طبقة HTTP المركزية؛ تضيف اللغة والتوكن ووقت الانتظار، وتحلل JSON والأخطاء والتنزيلات.
- `src/Apihooks/route.jsx`: تعريف routes الرئيسي، ويجب تحديثه عند إضافة شاشة لها مسار مستقل.
- `src/Apihooks/queryClient.js`: إعداد React Query المشترك.
- `src/Apihooks/use*.js`: هوكات الربط مع الباك إند للبيانات المتكررة مثل الداشبورد، الرسائل، الإشعارات، والفورمات.
- `src/Api/storage.js`: إدارة لغة الواجهة وتوكن الجلسة في `localStorage`.
- `src/Api/reportExportService.js`: توليد وتصدير مستندات التقارير فقط.
- `src/Api/formSubmissionExportService.js`: تصدير إجابات الفورمات إلى Excel أو PDF.
- `src/utils/formData.js`: تحويل البيانات والملفات إلى `FormData` بدون تكرار.
- `src/utils/exportHtml.js`: تنسيق النص والتاريخ والطباعة والتنزيل وقالب CSS المشترك للتصدير.
- `src/utils/sound.js`: صوت Toast وتسجيل الدخول.
- `src/index.css`: ملف الثيم الكامل. المتغيرات في `:root` هي المصدر الأساسي للألوان والأسطح والحدود.
- `src/config/environment.js`: يقرأ إعدادات البيئة الخاصة بعنوان API ووقت الانتظار.

### سجل حركات لوحة المهام

- تحفظ الحركات في جدول `task_activities` حتى تبقى عملية التدقيق متاحة بعد حذف المهمة نفسها.
- يسجل النظام إنشاء المهمة، تعديلها، نقلها بين الحالات، حذفها، إرفاق ملف، وحذف ملف مرفق.
- يحتوي كل سجل على منفذ الحركة، القسم، عنوان المهمة، وقت التنفيذ، والتفاصيل المرتبطة مثل الحالة السابقة والجديدة أو اسم الملف.
- مسار القراءة `GET /api/task-activities` يطبق نطاق صلاحيات اللوحة، ويدعم فلاتر `department_id`, `all`, `actor_id`, `action`, `from`, و`to`.
- مسؤولية إنشاء السجلات مركزية داخل `TaskActivityService`، وتعرضها الشاشة الجانبية في `Page/Tasks/index.jsx`.
- يوفر `TaskActivitySeeder` بيانات عرض موزعة زمنياً تشمل جميع أنواع الحركات والأفراد والأقسام، ويمكن تشغيله منفرداً عبر `php artisan db:seed --class=TaskActivitySeeder`.

### إضافة واجهة FrontEnd جديدة

1. أنشئ فولدر باسم التبويب داخل `src/Page/<Tab>/` وضع الصفحة الرئيسية في `index.jsx`.
2. انقل الأجزاء الكبيرة إلى `src/Page/<Tab>/components/` أو ملفات مساعدة داخل نفس التبويب حتى لا تتضخم الصفحة.
3. أضف استدعاءات الخادم العامة إلى المجموعة المناسبة داخل `Api/api.js`.
4. أضف Hook داخل `Apihooks/use*.js` عندما يكون الربط متكرراً أو يحتاج React Query.
5. حدّث `Apihooks/route.jsx` إذا احتاجت الواجهة مساراً مستقلاً.
6. استورد الصفحة داخل `Layout/AppShell.jsx` وأضف عنصر القائمة مع شرط الصلاحية المناسب.
7. أضف حالة العرض داخل منطقة `data-guide="content"`.
8. أضف شرح الواجهة إلى `helpJson/interfaceGuide.json` وإلى `Page/Guide/index.jsx`.
9. أضف النصوص إلى `i18n/translations.js` إذا كانت الواجهة ثنائية اللغة.
10. أضف CSS بأسماء خاصة بالصفحة لتجنب التأثير على بقية النظام.

### تدفق طلب API

مثال إنشاء تقرير:

1. `ReportFormModal.jsx` يجمع القيم.
2. `Api/api.js -> api.createReport()` يستعمل `Api/http.js` لإرسال `POST /api/reports`.
3. `AuthenticateApiToken` يحدد المستخدم، و`SetLocale` يحدد اللغة.
4. `StoreReportRequest` يتحقق من الصلاحية والحقول.
5. `ReportController` يمرر البيانات إلى `ReportRepositoryInterface`.
6. `ReportRepository` ينشئ التقرير ويربطه بالمستخدم والفرع والقسم.
7. `ReportResource` يعيد JSON ثابت البنية.
8. الواجهة تعيد تحميل البيانات وتعرض Toast نجاح.

### Modules

- `Modules/Organization`: يحتوي تقريباً كل منطق النظام التشغيلي، ومقسم بطبقات واضحة لتسهيل الاختبار والتطوير.
- `Modules/Locale`: وحدة صغيرة مسؤولة عن endpoint اللغة.
- `routes/api.php`: لا يعرّف المسارات يدوياً؛ يحمل تلقائياً كل `Modules/*/Routes/api.php`.
- `bootstrap/providers.php`: يسجل مزودي الوحدات حتى تعمل bindings والمسارات.

- `DashboardAnalyticsService.php`: يجمع تحليلات الرئيسية حسب الدور والنطاق: اتجاه التقارير لستة أشهر، توزيع الحالات، وضع المهام، والإجراءات التي تحتاج انتباه المستخدم.

طبقة Repositories تفصل Controllers عن تفاصيل Eloquent:

عند إضافة مصدر بيانات مختلف أو اختبار Mock يمكن استبدال التنفيذ لأن Controllers تعتمد Interfaces.

### Requests وResources

- ملفات `Requests/Store*` و`Update*` تحتوي قواعد التحقق عند الإنشاء والتعديل.

- `TransitionReportRequest` يتحقق من إجراء انتقال التقرير.
- `SyncRolePermissionsRequest` يتحقق من قائمة الصلاحيات.
- ملفات `Resources/` هي العقد النهائي مع FrontEnd؛ لا تُرجع الموديل الخام عندما توجد Resource مقابلة.

## 6. نماذج البيانات والعلاقات

### الهيكل التنظيمي

- `Branch` لديه عدة `Department`.
- `Department` يتبع `Branch` ولديه عدة `User` و`Task`.
- `Office` لديه عدة `User` وهو بديل تنظيمي مستقل عن الفرع والقسم.
- `User` قد يتبع فرعاً وقسماً أو مكتباً، ويحمل دوراً وصلاحيات.

### بيانات الموظف

- `UserAddress` علاقة one-to-one للعنوان.
- `UserFamilyDetail` علاقة one-to-one للبيانات العائلية والطوارئ.
- `UserPersonalDetail` علاقة one-to-one للبيانات الشخصية والقياسات ومقاسات الزي.

### التقارير والإشعارات

- `Report` يتبع الموظف والفرع والقسم، وله عدة `ReportAction`.
- `ReportAction` يسجل تاريخ انتقال التقرير والإجراء والملاحظة.
- `CndNotification` يتبع المستخدم وقد يرتبط بتقرير أو تعميم أو فورم منشور.

### الرسائل والمراسلات

- `Message` هي الرسائل الداخلية القديمة بعد إعادة تسميتها من المراسلات، وتربط مرسلاً ومستقبلاً ولها عدة `MessageReply`.
- `MessageReply` يدعم المحتوى والمرفقات، وتظهر الرسائل غير المقروءة عبر حقول قراءة خاصة بالمرسل والمستلم.
- `FormalCorrespondence` هو سجل المراسلة الرسمية، وفيه الاتجاه والحالة والموضوع والجهات الخارجية أو الداخلية المرتبطة.
- `FormalCorrespondenceEvent` يمثل محطة في السلسلة الزمنية: الجهة أو المكان، التاريخ، الحالة، والملاحظة.
- `FormalCorrespondenceDocument` يمثل وثيقة ضمن محطة زمنية، ويمكن أن تكون ملفاً مرفوعاً أو كتاباً صادراً عن مؤسستنا من قالب Word رسمي، مع مصدر وهدف لكل وثيقة.
- `ExternalEntity` يخزن الجهات الخارجية التي تظهر كمصدر أو هدف للمراسلات الرسمية.
- `Circular` يتبع المُصدر ويرتبط بالمستلمين عبر pivot `circular_recipients`.

### الفورمات

- `CustomForm` هو القالب وله عدة `CustomFormField`.
- `CustomFormPublication` نسخة نشر تحدد الجمهور والنطاق والفترة.
- `CustomFormSubmission` إجابة مستخدم محفوظة مع رقم نسخة و`payload` JSON.

### المهام والملفات

- `Task` يتبع قسماً ومنشئاً ومسؤولاً اختيارياً وله عدة ملفات.
- `DriveFile` يتبع الرافع، وقد يتبع قسماً أو مهمة، ويحفظ مساره الخاص ومسار نسخته العامة إن نُشر.
- `DriveFolder` يتبع المالك وقد يتبع مجلداً أباً، ويحمل مساره الفيزيائي والنطاق والمشاركة والرابط العام الموروث للمحتويات.
- مشاركة الملف مع مستخدمين تحفظ في `drive_file_shares`.
- مشاركة المجلد تحفظ في `drive_folder_shares`.
- الرابط العام المولّد يستخدم token قابل للإلغاء، ويُحفظ بجانبه مسار مباشر ثابت للنسخة المنشورة.

## 7. الوظائف الرئيسية وقواعد العمل

### دورة التقارير

```text
draft/returned -> department_review -> branch_review -> general_review -> approved
                         |                  |                  |
                         +-> returned       +-> returned       +-> returned
```

- ينطبق نفس المسار على التقارير وخطط العمل.
- الموظف/الفني ينشئ المسودة ويعيد إرسال التقرير المرتجع.
- رئيس القسم يراجع ما وصل إلى قسمه، ويمكنه الإرسال إلى مدير الفرع أو المدير العام أو الإعادة للموظف مع سبب.
- عند إرسال رئيس القسم إلى مدير الفرع أو المدير العام يختفي التقرير من قائمة رئيس القسم والموظف.
- مدير الفرع يراجع ما وصل إليه ضمن فرعه، ويمكنه الإرسال إلى المدير العام أو الإعادة للموظف.
- المدير العام يرى ما وافق عليه أو صدر له من رؤساء الأقسام أو مدراء الأفرع، ويعتمد نهائياً أو يعيد للموظف قبل الاعتماد.
- بعد الاعتماد يبقى التقرير ظاهراً للمدير العام ومدير قواعد البيانات، ويتعطل زر الإعادة للموظف.
- مدير قواعد البيانات يرى كل التقارير والخطط ويملك صلاحيات تعديل وانتقال كاملة.
- سبب الإعادة يحفظ مؤقتاً في كاش الباك إند ويظهر في تفاصيل التقرير المرتجع، ثم يحذف عند إعادة إرسال نفس التقرير.
- فلاتر التقارير في الواجهة تتدرج حسب الصلاحية: التاريخ للجميع، الموظف لرئيس القسم وما فوق، القسم لمدير الفرع وما فوق، والفرع للمدير العام ومدير قواعد البيانات.

### المهام

- المراحل: `archived` (مؤرشفة) ← `planned` ← `in_progress` ⇄ `communication` ← `review` ← `completed`، و`cancelled` خارج المسار.
- المراحل الجديدة أُضيفت إلى المسار ولم تُلغِ القديمة: المرحلة النهائية تبقى مخزَّنة `completed` وتُعرض «الاعتماد» لأنها لم تعد تُبلغ إلا بعد التدقيق. لا يُعاد تسمية أي قيمة قائمة ولا يُعدَّل أي سطر في سجل الحركات.
- تُنشأ المهمة مؤرشفة افتراضياً، وينقلها الموظف المكلّف إلى `planned` ثم `in_progress`.
- مرحلة التواصل: يحوّل المكلّف المهمة إلى موظف تواصل يُختار عند النقل (`communication_user_id`) ويصله إشعار. هو وحده (أو صاحب صلاحية التدقيق) من يخرجها منها: إما إعادتها إلى `in_progress` بملاحظة إلزامية، أو رفعها إلى `review`.
- الخروج من `review` إلى `completed` (الاعتماد) أو الإعادة منها يتطلب صلاحية `tasks.review`.
- الانتقالات محكومة بمسار واحد معرّف في `App\Modules\Tasks\Services\TaskWorkflow`، ويرسل `TaskResource` قائمة `allowed_transitions` لكل مستخدم فلا تعرض الواجهة حركة يرفضها الخادم.
- كل انتقال يُسجَّل في `task_stage_transitions` بتاريخه ووقته ومدة بقاء المهمة في المرحلة السابقة ومنفّذه وصاحبها وموظف تواصلها، وهو مصدر لوحة الإحصائيات.
- الأولويات: `low`, `medium`, `high`, `urgent`.
- الرؤية والتعديل مربوطان بالقسم ونطاق المستخدم.

### إحصائيات المهام

- تبويب مستقل (`/task-stats`) مقيَّد بصلاحية `tasks.statistics.view`، ممنوحة افتراضياً لرئيس القسم ومدير الفرع والمدير العام ومدير قواعد البيانات، وقابلة للمنح لموظف مشرف من صفحة الأدوار والصلاحيات.
- `GET /api/task-statistics` يقبل `department_id` أو `all=1` ومجال تاريخ `from`/`to`، ويعيد: ملخصاً عاماً، متوسط زمن كل مرحلة، صفاً لكل موظف (المنجز، المتأخر، زمن التنفيذ، زمن المهمة، مرات الإعادة من التواصل، نسبة الالتزام)، صفاً لكل موظف تواصل، ومنحنى الوارد مقابل المعتمد لثمانية أسابيع.
- نطاق الرؤية هو نفسه نطاق لوحة المهام (`ResolvesTaskScope`) فلا يرى أحد إحصاءات قسم لا يرى لوحته.

### إحصاءات الصفحة الرئيسية

- أرقام التقارير والمهام والفورمات والإشعارات تُحسب حسب الدور ونطاق الوصول نفسه المستخدم في الواجهات المتخصصة.
- يعرض مخطط زمني حركة إنشاء واعتماد التقارير خلال آخر ستة أشهر.
- يعرض توزيع حالات التقارير لمعرفة مكان التراكم في مسار الاعتماد.
- يعرض وضع المهام: المخطط، قيد التنفيذ، المكتمل، العاجل، المتأخر، وما يستحق خلال أسبوع.
- تعرض بطاقات الانتباه الإجراءات المباشرة: الإشعارات غير المقروءة، التقارير المرتجعة، المهام العاجلة، والفورمات غير المعبأة.

### الفورمات المخصصة

- الأنواع المدعومة: text, email, password, date, select, textarea, number, checkbox.
- جمهور النشر يدعم المدراء، الرؤساء، الموظفين، المثبتين، العقود، أو الجميع.
- النطاق: المؤسسة، الفرع، أو القسم.
- يمكن للمستخدم إرسال أكثر من نسخة؛ لا تضيع الإجابات السابقة.

### الملفات

- النطاقات: شخصي، قسم، مهمة، أو المؤسسة كاملة.
- يمكن لجميع المستخدمين إنشاء مجلدات ومجلدات فرعية ورفع الملفات داخلها.
- إنشاء المجلد في الواجهة ينشئ مجلداً حقيقياً داخل `BackEnd/storage/app/private/drive/users/{user_id}`، وتُبنى المجلدات الفرعية تحته فعلياً.
- تحفظ الملفات على القرص باسمها الأصلي بعد إزالة المحارف غير الصالحة للمسارات؛ وعند تكرار الاسم يضاف رقم مثل `(2)` دون الكتابة فوق الملف السابق.
- يرث الملف أو المجلد الفرعي نطاق الوصول والمشاركة والرابط العام من المجلد الأب.
- يمكن مشاركة الملف مع مستخدمين محددين أو قسم أو فرع.
- يمكن مشاركة المجلد مع مستخدمين أو قسم أو فرع، فتظهر كامل محتوياته لهم.
- عند النشر العام تنشأ مرآة فعلية داخل `BackEnd/storage/app/public/drive-public` بنفس بنية المجلدات والأسماء، ويصبح لكل ملف `direct_url` ثابت يمكن استخدامه من أي برنامج.
- يبقى رابط الـ token في `public_url` متاحاً وقابلاً للإلغاء إلى جانب `direct_url`، وإلغاء النشر يحذف النسخة العامة فقط ويحافظ على الأصل الخاص.
- رابط `preview_url` يعرض الملف داخل المتصفح للمستخدم المصرح له، وأيقونة العين في بطاقة الملف تستخدمه لمعاينة الصور وPDF وباقي الأنواع التي يدعمها المتصفح.
- مدير قواعد البيانات ينشئ المجلدات ويرفع الملفات بنطاق المؤسسة تلقائياً، فتظهر لجميع المستخدمين.
- صلاحية التنزيل والحذف تفحص في الخادم.

### الرسائل الداخلية الفورية

- مسارات الرسائل هي `GET/POST /api/messages` و`POST /api/messages/{message}/replies`.
- يمكن إرفاق ملف مع الرسالة ومع الرد، ويعرض المتصفح الصور مباشرة ويفتح أو ينزل الملفات الأخرى.
- يستخدم النظام Laravel Reverb وLaravel Echo لبث الرسالة أو الرد فورياً إلى قناة `private-user.{id}`.
- عند توقف Reverb لا يفشل إنشاء الرسالة؛ يسجل الخادم warning فقط ويستمر الطلب.
- `GET /api/messages/unread-count` يعيد عدد الرسائل غير المقروءة للسايد بار.
- `PATCH /api/messages/{message}/read` يطفئ إشارة غير المقروء عند فتح الرسالة.
- `DELETE /api/messages/{message}` يحذف الرسالة من المصدر للمرسل فقط.

### المراسلات الرسمية

- المراسلات الرسمية منفصلة عن الرسائل الداخلية وتدار من `Page/FormalCorrespondences/index.jsx`.
- الاتجاهات المدعومة حالياً:
  - من مؤسسة خارجية لمؤسسة خارجية.
  - من مؤسسة خارجية لمؤسستنا.
  - من مؤسستنا لمؤسسة خارجية.
  - من مؤسستنا لفرع أو قسم داخلي.
- كل مراسلة تبدأ بعنوان ومرجع `reference_code` وحالة واتجاه، ثم تعرض خط سير زمني مرتب.
- كل محطة زمنية يمكن أن تحمل عدة وثائق، ولكل وثيقة مصدر وهدف وعنوان.
- نوع الوثيقة إما `uploaded` لملف ضمن السلسلة أو `internal_letter` ككتاب صادر عن مؤسستنا من قالب Word رسمي.
- توليد `internal_letter` يعبئ قالب Word، يضيف QR مع شعار المؤسسة أو نصها، ويدرج التوقيع الرقمي لصاحب التوقيع المناسب كصورة عائمة داخل مساحة التوقيع.
- قوالب Word الرسمية موجودة في `BackEnd/resources/templates/documents/`، وملف التوثيق التفصيلي لها في `BackEnd/resources/templates/README.md`.
- عند تعديل القوالب الرسمية يفضل أخذ نسخة احتياطية داخل `BackEnd/resources/templates/backups/` قبل إعادة البناء.
- البيانات التجريبية لهذه الميزة موجودة في `FormalCorrespondenceSeeder.php`.

لتفعيل الروابط المباشرة بعد تثبيت المشروع يجب تنفيذ:

```bash
cd BackEnd
php artisan storage:link
```

## 8. المصادقة والصلاحيات والنطاق

- `AuthenticateApiToken.php` يقرأ Bearer token ويضع المستخدم في الطلب.
- الصلاحيات تُنشأ في `RolePermissionSeeder.php`.
- الأدوار: employee, technician, department_head, branch_manager, general_manager, database_manager.
- `spatie/laravel-permission` هو مصدر التحقق من `can(...)`.
- `OrganizationScopeService` يحدد ما يستطيع المستخدم رؤيته أو إدارته مكانياً.
- `ReportAccessService` يطبق نطاقاً مستقلاً للتقارير.
- يجب عند إضافة endpoint حساس استخدام Permission واضحة **وخدمة نطاق** إن كانت البيانات مرتبطة بفرع أو قسم.

## 9. قاعدة البيانات وMigrations

- كل تغيير في المخطط يجب أن يضاف Migration جديد؛ لا تعدّل Migration قديم بعد استخدامه في بيئة مشتركة.
- migrations الأساسية تنشئ users/cache/jobs ثم الفروع والأقسام والتقارير والإشعارات والبيانات الإضافية.
- migrations اللاحقة تضيف المكاتب والمراسلات والتعاميم والفورمات والمهام والدرايف.
- migrations الحديثة تعيد تسمية المراسلات الداخلية القديمة إلى `messages`، وتضيف `formal_correspondences` و`formal_correspondence_events` و`formal_correspondence_documents`.
- `DatabaseSeeder.php` هو نقطة تشغيل seeders الأخرى.
- `RolePermissionSeeder.php` ينشئ الصلاحيات ويربطها بالأدوار.
- `OfficeSeeder.php` ينشئ المكاتب الابتدائية.
- `TaskSeeder.php` يضيف بيانات مهام تجريبية.
- `FormalCorrespondenceSeeder.php` يضيف مؤسسات خارجية ومراسلات رسمية بسلاسل زمنية ووثائق تجريبية.

أوامر مفيدة:

```powershell
cd BackEnd
php artisan migrate
php artisan migrate:fresh --seed
php artisan db:seed
php artisan db:seed --class=FormalCorrespondenceSeeder
php artisan route:list --path=api
php artisan test
```

> `migrate:fresh` يحذف الجداول والبيانات؛ استخدمه فقط على قاعدة تطوير يمكن فقدها.

## 10. متغيرات البيئة والتشغيل

### FrontEnd

راجع `FrontEnd/src/config/environment.js` لمعرفة أسماء متغيرات Vite المستخدمة. يجب أن يبدأ متغير Vite بالبادئة `VITE_` ليظهر داخل التطبيق.

إعداد التطوير الحالي محلي داخل `FrontEnd/.env`:

```env
# Server: VITE_DEV_API_TARGET=http://172.116.10.20
VITE_DEV_API_TARGET=http://127.0.0.1:8000
```

أبقِ إعداد الخادم السابق معلّقاً، وفعّل السطر المناسب فقط عند تبديل بيئة التشغيل.

### BackEnd

أهم القيم في `.env`:

- `APP_ENV`, `APP_KEY`, `APP_DEBUG`, `APP_URL`
- `DB_CONNECTION` وبقية إعدادات قاعدة البيانات
- `FILESYSTEM_DISK` لتخزين الملفات
- إعدادات cache/session/logging

القيم الحالية مضبوطة للتطوير المحلي (`APP_ENV=local`, `APP_DEBUG=true`, `APP_URL=http://127.0.0.1:8000`) مع إبقاء قيم الخادم السابقة كتوضيح معلّق داخل `BackEnd/.env`.

بعد تغيير إعدادات Laravel:

```powershell
php artisan config:clear
php artisan cache:clear
php artisan storage:link
```

## 11. الجولة الإرشادية ودليل الواجهات

- الجولة موجودة في `FrontEnd/src/Components/InterfaceGuide.jsx`.
- تظهر تلقائياً مرة واحدة فقط على الجهاز باستخدام المفتاح `cnd-interface-guide-v2-completed` في `localStorage`.
- الجولة تبني خطواتها من التبويبات المتاحة فعلياً للمستخدم، لذلك لا تعرض واجهات لا يملك صلاحيتها.
- عند الضغط على **تخطي الجولة** أو إغلاقها تحفظ حالة الإنهاء وتتوقف فوراً.
- تبويب **دليل الواجهات** متاح للجميع من `Page/Guide/index.jsx`.
- زر **إعادة تشغيل الجولة** في الدليل يحذف حالة الإنهاء ويبدأ الجولة يدوياً.

عند إضافة واجهة جديدة يجب تحديث `FrontEnd/helpJson/interfaceGuide.json` وبيانات `FrontEnd/src/Page/Guide/index.jsx`.

## 13. قواعد التطوير والصيانة

- ضع قواعد الأعمال المركبة في Service، لا داخل React أو Controller.
- ضع الوصول المتكرر للبيانات خلف Repository قائم أو جديد.
- لا تثق بأي `branch_id` أو `department_id` مرسل من الواجهة دون تحقق نطاق في الخادم.
- حدّث Resource واستخداماته في صفحات JavaScript معاً عند تغيير شكل JSON.
- أعد استخدام `ReusableFormModal` للفورمات البسيطة الموحدة.
- لا تضف منطقاً جديداً داخل `lib.js`؛ استخدم `Api/` لمنطق التكامل و`utils/` للمساعدات عديمة الحالة.
- حافظ على ملفات الخدمات محددة المسؤولية؛ مثال: تصدير التقارير منفصل عن تصدير الفورمات.
- حافظ على ألوان الثيم عبر متغيرات CSS بدل قيم جديدة متناثرة.
- لا تضف تبويباً إدارياً دون شرط صلاحية في الواجهة وتحقق مقابل في الباك إند.
- أضف Migration وSeeder عند الحاجة، ولا تعتمد على بيانات موجودة يدوياً.
- حدّث هذا الدليل ودليل الواجهات عند إضافة وظيفة تؤثر على المطور أو المستخدم.
